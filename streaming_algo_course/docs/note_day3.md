# Заметка: Bloom Filter и Count-Min Sketch (День 3) – актуальная версия

## 1) Что реализовано
- **Bloom Filter** (`internal/bloom`):
  - Классический вероятностный фильтр Блума.
  - Методы `Add` и `MayContain` (гарантия отсутствия false negative).
  - Генерация k хеш-функций через double hashing (2 независимых хеша FNV-1 и FNV-1a).
  - Автоматический расчёт оптимальных параметров `m` и `k` по заданному числу элементов `n` и допустимой вероятности ложного срабатывания `p` (функции `OptimalParams` и `NewWithOptimal`).
  - Защита от нулевого размера или количества хеш-функций, проверка `key == nil`.
- **Count-Min Sketch** (`internal/stream`):
  - Структура для оценки частоты элементов (Top Talkers).
  - Фиксированная память: матрица счётчиков `depth × width`.
  - Каждая строка использует независимую хеш-функцию на основе FNV-1a с добавлением `seed + i`.
  - Гарантия: оценка никогда не занижает истинную частоту.
  - Защита от нулевых `width` или `depth`, проверка `key == nil`.

## 2) Инварианты и семантика
- **Bloom Filter**:
  - `Add(key)` устанавливает `k` битов в массиве.
  - `MayContain(key)` возвращает `false`, если ключа точно нет, и `true` – если возможно есть (вероятность ложного срабатывания ≤ заданной `p`).
  - Ложноотрицательные срабатывания невозможны при условии корректной работы хеш-функций.
- **Count-Min Sketch**:
  - `Add(key)` увеличивает счётчики во всех `depth` строках на позиции `hash_i(key) % width`.
  - `Estimate(key)` возвращает минимальное значение среди этих счётчиков (оценка частоты).
  - Оценка всегда ≥ истинного числа добавлений (overestimate допустим из-за коллизий).
- Оба пакета не содержат глобального состояния, потокобезопасность не требуется по условию.

## 3) Принятые решения

### Bloom Filter
- **Double hashing**: используется `hash1` (FNV-1a) и `hash2` (FNV-1).  
  Позиция для i-й хеш-функции: `pos = (h1 + i * h2) % m`.  
  Это даёт хорошее распределение и избегает вычисления k независимых хешей (экономия CPU).
- **Коррекция `hash2`**: если `hash2 == 0`, устанавливаем в 1, иначе делаем нечётным (`hash2 |= 1`), чтобы избежать вырожденных последовательностей.
- **Выбор параметров**:
  - Формулы:  
    `m = ceil( -n * ln(p) / (ln2)^2 )`,  
    `k = round( (m/n) * ln2 )`.
  - По умолчанию при ручном создании `New(m, k)` параметры фиксированы. Для автоматического подбора – `NewWithOptimal(n, p)`.
  - В исследовательском тесте (DDoS атака) рекомендуется выбирать `p = 0.01` (1% false positives) и `n` равным количеству уникальных ключей в SSTable.

### Count-Min Sketch
- **Хеш-функции**: FNV-1a с добавлением seed. Для каждой строки `i` используется `seed + i` (переполнение допустимо, даёт разные хеши).
- **Выбор `width` и `depth`**:
  - `width` влияет на точность: ошибка по частоте ~ `(total_count) / width` с вероятностью, определяемой `depth`.
  - `depth` – количество независимых хешей, уменьшает вероятность сильного завышения.
  - Типичный компромисс: `width = 1000`, `depth = 5` для общего числа элементов до миллиона.
  - В задании не требуется автоматический подбор, но в заметке обосновывается выбор (например, "10 КБ памяти → width = 2048, depth = 4").

### Обработка ошибок
- Все публичные методы возвращают `error` вместо паники.
- Проверка на `key == nil` (возвращается ошибка).
- В конструкторах некорректные параметры (0) заменяются на 1, чтобы избежать деления на ноль или пустых структур.

## Результаты бенчмарка с эмуляцией дисковых задержек
Для демонстрации эффективности Bloom‑фильтра в условиях, приближенных к реальным, был создан бенчмарк `BenchmarkDDoSWithMockTables`. Каждый вызов `Lookup` симулирует задержку случайного чтения с диска (50 микросекунд). Тест создаёт 200 SSTable и выполняет поиск отсутствующего ключа (DDoS-атака).

**Результаты запуска на Intel i5-1155G7:**

| Режим                 | время на операцию | относительное ускорение |
|-----------------------|------------------|-------------------------|
| Без Bloom‑фильтра      | 118 621 067 ns/op | 1x                      |
| С Bloom‑фильтром       |  2 516 107 ns/op | **~47x**                |

### Объяснение

- **Без фильтра** – каждый из 200 SSTable обязательно читается с диска (эмулируемая задержка 50µs × 200 = 10 мс, но реальное время больше из-за накладных расходов цикла и вызовов). Итоговое время ~118 мс.
- **С фильтром** – благодаря вероятности ложного срабатывания 1%, фильтр пропускает в среднем только 2 файла из 200 (200 * 0.01 = 2). Остальные 198 проверок завершаются в памяти без обращения к диску. Время сокращается до ~2.5 мс.

### Значимость для реальных систем

В системах anti‑fraud, где на каждый запрос приходится проверять наличие IMSI в черном списке, 99.9% запросов – к отсутствующим ключам. Использование Bloom‑фильтра позволяет:

- Снизить нагрузку на диск в десятки раз.
- Увеличить пропускную способность системы (больше запросов в секунду).
- Уменьшить задержки ответа (latency).

Таким образом, интеграция Bloom‑фильтра в LSM-движок – критическая оптимизация для production-сред.

## 5) Ответы на вопросы задания

### Вопрос 1 (из day3.md неявный): Как выбрать m и k для Bloom Filter?
**Ответ:** Исходя из ожидаемого количества элементов `n` и допустимой вероятности ложного срабатывания `p`.  
Оптимальные значения:  
`m = ceil( -n * ln(p) / (ln2)^2 )` бит,  
`k = round( (m/n) * ln2 )` хеш-функций.  
Например, для `n = 10 000`, `p = 0.01` получаем `m ≈ 95851` бит (~12 КБ), `k = 7`.  
В коде это реализовано в функции `OptimalParams`.

### Вопрос 2: Почему Count-Min Sketch никогда не занижает частоту, но может завышать?
**Ответ:** Для каждого элемента в каждой строке выбирается одна ячейка, счётчик которой увеличивается.  
При оценке берётся минимум по всем строкам. Из-за коллизий в одной строке счётчик может быть больше истинного (если другие ключи попали в ту же ячейку).  
Но поскольку во всех строках значения счётчиков не меньше истинной частоты (минимум не может быть меньше), гарантируется, что оценка ≥ истинной частоты.

### Вопрос 3: Каковы типичные применения Bloom Filter и CMS вместе?
**Ответ:** В LSM-хранилище (как в днях 1–2) Bloom Filter для каждого SSTable позволяет избежать лишних чтений диска для несуществующих ключей.  
Count-Min Sketch можно использовать для мониторинга «горячих» ключей в реальном времени (например, частотность IMSI) без хранения всей статистики.

## 6) Известные ограничения и возможные улучшения
- **Bloom Filter**:
  - Использует double hashing – хороший компромисс, но для очень высоких требований к равномерности можно вычислять k независимых хешей (дороже).
  - Нет поддержки удаления (это особенность стандартного фильтра Блума).
- **Count-Min Sketch**:
  - Оценка всегда завышена, что может давать ложные срабатывания при поиске Top-K (необходимо дополнительное ранжирование).
  - Для точного определения Top-K нужно хранить кучу из кандидатов (например, с использованием `container/heap`).
- **Общее**:
  - Отсутствие автоматической подстройки параметров под нагрузку (можно добавить адаптивные алгоритмы).
  - При многопоточном доступе потребуется синхронизация (добавление мьютексов или атомарных операций).

## 6.1) Улучшение использовать «консервативное обновление» при добавлении ключа

AddConservative добавляет ключ, используя адаптивный алгоритм «консервативного обновления» (Conservative Update / Minimal Increment). В отличие от обычного Add, инкрементируются только те ячейки, которые на данный момент содержат минимальное значение среди всех хеш-позиций ключа. Это автоматически снижает завышение оценки при коллизиях и улучшает точность без изменения основных параметров (width/depth). Алгоритм адаптируется к текущей нагрузке, так как величина инкремента зависит от заполненности скетча.

  Для каждого уникального ключа вычислялась относительная ошибка:
(|оценка − истина|) / истина.
Так как оба метода гарантируют оценка ≥ истина, ошибка всегда неотрицательна и показывает, во сколько раз скетч завышает частоту. Полученные ошибки усреднялись по всем 1000 ключам.

Результат (50 тыс. вставок, width=200, depth=4, Ципф 1.5):
Классический Add: 3.72
AddConservative: 2.28

Почему так происходит:
Классический Add при каждой вставке увеличивает все depth счётчиков, поэтому любая коллизия немедленно «раздувает» оценку на 1 по всем хеш-позициям.
AddConservative инкрементирует только минимальные счётчики. Это означает, что если ключ уже имеет коллизии, его оценка растёт лишь в тех ячейках, которые и так показывают наименьшее значение, — алгоритм адаптивно сдерживает завышение, не трогая перегруженные коллизиями ячейки.
В результате ошибка снижается в 1.6 раза при полном сохранении гарантии «никогда не занижать».

## Результаты нагрузочного тестирования с Count-Min Sketch

Для проверки работы CMS в реальных   условиях была выполнена команда:

```bash
go run ./cmd/kvtool load -count 100000 -zipf 1.1 -report
```

Параметры:
- 100 000 операций (50 000 `Put` + 50 000 `Get`).
- Zipf-распределение с `s=1.1` на 1000 уникальных ключей.
- CMS: `width=2048`, `depth=4`, память ≈ 64 КБ.

**Результат – топ-10 ключей по оценённой частоте:**

```
 1. user_00000000 ~ 17669
 2. user_00000001 ~ 8488
 3. user_00000002 ~ 5346
 4. user_00000003 ~ 3927
 5. user_00000004 ~ 3083
 6. user_00000005 ~ 2431
 7. user_00000006 ~ 2073
 8. user_00000007 ~ 1888
 9. user_00000008 ~ 1663
10. user_00000009 ~ 1486
```

**Анализ:**

- **Перекос распределения**: первый ключ получил ≈35% всех вставок, второй – 17%, третий – 10.7%. Это точно соответствует Zipf(1.1).
- **Полнота охвата**: сумма оценок топ-10 = 48 054, что составляет 96% от общего числа `Put` (50 000). Оставшиеся 990 ключей разделили между собой ~4% вставок – типичное поведение «длинного хвоста».
- **Точность CMS**: теоретическая погрешность `total/width ≈ 50000/2048 ≈ 24.4`. Даже при таком завышении топ-10 остаётся стабильным – все ключи из топа не могут «выпасть» из-за ошибки, так как разрыв между 10-м и 11-м ключом велик.
- **Производительность**: 100 000 операций выполнено за **45.8 мс** → **2.18 млн ops/s**. На memmap-хранилище CMS добавляет незначительную задержку (4 хеш-функции и 4 инкремента на `Add`).

**Вывод:** Count-Min Sketch успешно идентифицирует «горячие» ключи в потоке, потребляя фиксированный объём памяти (64 КБ), что позволяет использовать его для мониторинга Top‑Talkers в реальном времени даже при миллионах уникальных абонентов.
