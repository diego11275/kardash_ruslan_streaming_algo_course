## Заметка по реализации SkipList (Day 1)

### 1) Что реализовано
- **Пакет:** `internal/skiplist`.
- **Компоненты:** структура `SkipList`, узел `skipListNode`, ленивый итератор `scanIterator`, реализующий интерфейс `Iterator`.
- **Операции:**
  - `Put(key, value []byte) error` – вставка или обновление ключа.
  - `Get(key []byte) ([]byte, error)` – чтение значения по ключу, возвращает `ErrNotFound` при отсутствии.
  - `Delete(key []byte) error` – удаление ключа.
  - `Scan(start, end []byte) (Iterator, error)` – диапазонный итератор.

### 2) Инварианты и семантика
- **Обновление ключа:** повторный `Put` с тем же ключом перезаписывает значение, не создавая новый узел. Ключи остаются уникальными.
- **Scan:** работает как полуинтервал `[start, end)`.  
  - `start == nil` → начало списка (минус бесконечность).  
  - `end == nil` → до конца списка (плюс бесконечность).  
  - Итератор ленивый: не копирует данные заранее, а последовательно обходит узлы по базовому уровню.
- **Отсутствующие ключи:** `Get` и `Delete` возвращают `ErrNotFound`. Итератор при пустом диапазоне возвращает `ok = false`.

### 3) Принятые решения (и почему)
- **maxLevel = 20** – фиксированная константа. Для ожидаемого объёма данных до ~1 млн элементов (2²⁰) обеспечивает логарифмическую высоту без избыточного расхода памяти. Альтернативы (зависимость от N или параметр конструктора) не потребовались в рамках прототипа.
- **p = 0.5** – классическая вероятность для SkipList. Даёт хороший баланс между высотой (ожидаемое ~log₁/ₚ N) и количеством указателей. При p=0.5 каждый следующий уровень встречается вдвое реже, что соответствует идее «честной монетки».
- **Генерация уровня:** coin‑flip (геометрическое распределение) через цикл `rand.Float64() < p`. Простота и наглядность; не требуется предварительная таблица.
- **Хранение данных:** копирование ключа и значения при `Put` (`append([]byte(nil), ...)`). Это идиоматичный для Go способ обеспечить иммутабельность данных внутри структуры – внешние модификации среза не влияют на хранимые значения. Плата – дополнительные аллокации, но для прототипа это допустимо.
- **Детерминизм:** генератор `rand.Rand` инициализируется переданным `seed`, что обеспечивает воспроизводимость последовательностей уровней. Критично для отладки и прохождения тестов.
- **Головной узел:** фиктивный узел с `next` длины `maxLevel`, упрощает алгоритмы (не нужны проверки на `nil` для начала списка).


### 4) Контроль (как проверялось)
- **Тесты:**  
  - `TestSkipList_BasicCRUD` – проверяет вставку трёх ключей, чтение, обновление (неявно, т.к. повторный `Put`), удаление и корректное возвращение `ErrNotFound`.  
  - `TestSkipList_ScanOrderAndRange` – проверяет, что `Scan` возвращает упорядоченные ключи в полуинтервале `[b, d)` и корректно останавливается.
- **Дополнительные тесты (уровень B/C):**  
  - Крайние случаи: `start > end`, пустые ключи, `start = nil`, `end = nil`, диапазон, не содержащий элементов.  
  - Повторные `Put` одного ключа.  
  - `Delete` несуществующего ключа.  
  - Итератор при закрытии.
- **Бенчмарки:**  
  - `BenchmarkPut` – суммарное время последовательной вставки N = 100 000 … 583 333.  
  - `BenchmarkDelete` – суммарное время удаления N элементов (предварительно заполненный список, случайный порядок удаления).  
  - Тренд: оба бенчмарка демонстрируют рост `O(N log N)`, что подтверждается аппроксимацией кривой `C·N·log₂N`.

### 5) Известные ограничения
- **Однопоточность:** реализация не использует синхронизацию (блокировки, атомарные операции). При конкурентных чтениях/записях могут возникнуть гонки данных.
- **Фиксированный maxLevel:** при вставке > 2²⁰ элементов максимальный уровень может стать недостаточным, что ухудшит производительность до O(N). В полноценной системе стоило бы выбирать maxLevel динамически, например, `ceil(log₂(ExpectedN))`.
- **Отсутствие сжатия/компактизации:** удалённые узлы не возвращаются в пул памяти (нет `sync.Pool`). При частых удалениях может расти фрагментация.
- **Копирование данных:** каждое `Put` создаёт новые копии ключа и значения. Для очень больших значений (например, профиль абонента с историей) это может быть накладно. В production можно рассмотреть хранение ссылок с гарантией неизменяемости извне.
- **Нет персистентности:** данные хранятся только в памяти, при перезапуске приложения теряются (это прототип HLR, следующий день будет добавлять WAL и SSTable).
