# Заметка: LSM-хранилище (День 2) – актуальная версия

## 1) Что реализовано
- **WAL** (`internal/wal`): журнал упреждающей записи, формат length‑prefixed, восстановление при старте.
- **SSTable** (`internal/sstable`): неизменяемые файлы с разреженным индексом, поддержка Put/Delete.
- **Memtable**: на основе `skiplist`, обеспечивает упорядоченность и быстрый доступ.
- **LSM Engine** (`internal/lsm`):
  - Координация записи: WAL → Memtable → SSTable (flush при превышении порога).
  - Восстановление из WAL после аварийного рестарта.
  - **Фоновый compaction** (L0 → L1) с устранением дубликатов и tombstone.
- **Обёртка `lsmstore.Store`**: реализует интерфейс `kv.Store` для использования в тестах и бенчмарках.

## 2) Инварианты и семантика
- `Put` добавляет новую версию ключа; при чтении возвращается самая свежая.
- `Delete` записывает tombstone (nil‑значение).
- `Scan([start, end))` возвращает упорядоченный поток ключей без дубликатов и tombstone.
- `Get` возвращает `kv.ErrNotFound` для отсутствующего или удалённого ключа.
- Все операции потокобезопасны (один мьютекс + фоновый воркер компакшена).

## 3) Принятые решения
### WAL
- Запись: `totalLen(4B) + opType(1B) + keyLen(4B) + key + valLen(4B) + value`.  
- При восстановлении битые хвосты игнорируются.  
- После успешного flush’а WAL корректно обрезается: старый writer закрывается (сброс буфера), выполняется `Truncate(0)`.

### SSTable
- Данные: последовательность `recordType + keyLen+key + (valLen+value для Put)`.  
- Разреженный индекс: каждая 64‑я запись запоминает смещение.  
- Footer: смещение индекса (8B) + magic (4B).  
- Итератор использует индекс для пропуска блоков вне диапазона.

### Компакшен (L0 → L1)
- **Фоновый режим**: горутина ожидает сигнала от `maybeCompact()`.  
- Условие: количество L0‑файлов ≥ `L0CompactThreshold` (по умолчанию 4).  
- Слияние: все L0 + существующий L1 → новый L1 (временный файл, атомарное переименование).  
- Старые L0‑файлы удаляются физически, L1 заменяется.

### Обработка ошибок и краевых случаев
- `key == nil` в `Put`/`Delete` → возвращается ошибка (не паника).  
- Пустые значения разрешены (`[]byte{}`).  
- Итератор корректно отрабатывает `start == end`, `start > end`, `start == nil`, `end == nil`.

## 4) Контроль и тестирование
- **Crash‑тест**: запись → SIGKILL → рестарт → данные восстанавливаются из WAL.  
- **Compaction‑тест**: повторная запись одного ключа → после компакшена остаётся одна запись.  
- Edge‑тесты: пустые ключи/значения, диапазоны, перезапись, удаление, tombstone после flush.  
- Бенчмарки:
  - `BenchmarkPutSync` / `BenchmarkPutNoSync` – влияние fsync.  
  - `BenchmarkGet` – точечное чтение.  
  - `BenchmarkScanRange` – диапазонный скан.  
  - `BenchmarkPutLSMNoSync` / `BenchmarkDeleteLSM` – тренд O(N).

## 5) Ответы на вопросы задания (обязательные)
### Вопрос 1: Если делать compaction очень часто, что страдает: CPU, диск (запись) или диск (чтение)?
**Ответ:** Страдает **CPU** (на слияние и сортировку) и **диск (запись)** из‑за многократной перезаписи одних и тех же данных (write amplification). Чтение страдает меньше, но может замедлиться из‑за частых блокировок.

### Вопрос 2: Почему для CDR‑данных (пишем много, читаем редко) выгодно откладывать compaction?
**Ответ:** Отложенный компакшен снижает write amplification и нагрузку на диск/CPU, так как данные успевают накопиться в нескольких L0‑файлах. Поскольку чтения редки, временное увеличение числа файлов не критично, а экономия ресурсов на записи позволяет обрабатывать более высокий поток вставок.

## 6) Известные ограничения и возможные улучшения
- **Отсутствие блум‑фильтра**: точечный `Get` может просматривать все L0‑файлы.  
- **Один уровень L1** – для больших объёмов данных потребовалась бы многоуровневая иерархия.  
- **Синхронный flush** – может временно блокировать запись.  
- **Нет сжатия блоков** – можно добавить snappy/lz4 для уменьшения размера SSTable.
